# ПУЛЬС — этап 1.2. Единая ролевая модель

## Что вошло в этап

1. Название интерфейса изменено на **ПУЛЬС**. Вход, стартовая настройка и шапка используют утверждённый файл фирменного логотипа `public/assets/puls-logo-approved.png` без перерисовки знака.
2. Добавлен слой `portal_role`, независимый от существующего `profiles.role`. Операционная роль старой диспетчерской сохранена.
3. Добавлены должности для системной роли «Диспетчер»: «Диспетчер», «Руководитель РЦ», «Старший смены РЦ».
4. Зафиксирована матрица модулей в `portal_role_modules` и создана серверная функция `has_portal_module_access(text)`.
5. Обновлены Edge Functions создания и изменения пользователя. Суперадминистратора может назначить только действующий суперадминистратор.
6. Для Техника и БЕ добавлена отдельная стартовая страница с предусмотренными матрицей модулями. Действующие операции транспортных заявок для этих двух ролей пока не открываются.
7. Ужесточены политики профилей, заявок, вложений и уведомлений. Прямое клиентское изменение роли или привязок профиля запрещено; клиент может менять только `is_active`, с ограничениями. Для Техника и БЕ закрыта подписка на старые push/realtime-каналы диспетчерской; их старые push-подписки очищаются при назначении роли.

## Матрица доступа модулей

| Роль портала | Заявки | Журнал диспетчера | Клиентская доставка | Складская логистика | Отгрузка РЦ |
|---|---:|---:|---:|---:|---:|
| Суперадминистратор | ✓ | ✓ | ✓ | ✓ | ✓ |
| Администратор | ✓ | ✓ | ✓ | ✓ | ✓ |
| Техник | — | — | ✓ | ✓ | — |
| УТЗ | ✓ | — | — | — | — |
| Диспетчер | ✓ | ✓ | — | — | ✓ |
| БЕ | ✓ | — | ✓ | ✓ | — |
| Заказчик | ✓ | — | — | — | — |

Руководитель РЦ и Старший смены РЦ используют системную роль «Диспетчер», а их должность хранится отдельно в `position_title`.

## Важное разделение ролей

- `profiles.role` — прежняя операционная роль (`customer`, `dispatcher`, `utz`, `admin`); она продолжает управлять логикой действующего модуля заявок.
- `profiles.portal_role` — роль в общей оболочке ПУЛЬС и в матрице модулей.
- Для ролей `technician` и `be` поле `profiles.role` сохраняется как `customer` только для совместимости типов старой схемы, но `current_role()` возвращает `NULL`. Это закрывает чтение и изменение старых заявок и их вложений для этих ролей до согласования их операционных прав.
- `super_admin` сохраняет старые административные возможности через совместимое отображение в `current_role() = 'admin'`, но отдельно проверяется на сервере через `is_super_admin()`.

## Порядок внедрения

1. Сделайте резервную копию базы данных Supabase проекта ПУЛЬС.
2. Проверьте, что миграции `0001`–`0011` уже применены именно в базе проекта ПУЛЬС.
3. Выполните `supabase/migrations/0012_portal_roles_and_module_access.sql` в SQL Editor или через штатный Supabase CLI.
4. Назначьте первый аккаунт суперадминистратора вручную в SQL Editor, заменив логин на существующий логин доверенного администратора:

   ```sql
   update public.profiles
      set portal_role = 'super_admin',
          role = 'admin',
          position_title = null
    where username = 'YOUR_EXISTING_ADMIN_LOGIN';
   ```

   Запрос должен изменить ровно одну строку. Не назначайте эту роль обычным администраторам.
5. Разверните обновлённые функции `admin-create-user` и `admin-update-user` из папки `supabase/functions`.
6. Соберите и разверните frontend.
7. Проверьте вход под каждым типом роли, доступность модулей и невозможность для Техника/БЕ открыть старый модуль заявок напрямую.

## Проверки и ограничения текущего этапа

- Миграция добавлена в проект, но не применена к вашей удалённой базе из этой рабочей среды.
- Edge Functions подготовлены в проекте, но не развернуты в Supabase.
- Новые модули «Журнал диспетчера», «Клиентская доставка», «Складская логистика» и «Отгрузка РЦ» пока не реализованы как рабочие процессы. Портал показывает их по матрице, а Технику и БЕ — безопасную страницу модулей.
- Детальные действия внутри новых модулей (создание, редактирование, подтверждение, отмена, согласование) матрица не описывает; их нужно согласовать отдельно до разработки.
- Механика календаря, заявок, слотов, отчётов, вложений и существующих триггеров не переписывалась.
