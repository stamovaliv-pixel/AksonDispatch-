# Аксон Логистика — портал заказа транспорта БЕ → РЦ

Обновлённая версия портала на основе визуальной системы «Аксон ДокСлот». Проект самостоятельный: отдельный GitHub-репозиторий, отдельный Supabase-проект и отдельные пользователи. Код и база действующего «Аксон ДокСлот» не изменяются.

## Что вошло в эту версию

- React + TypeScript + Vite; публикация подготовлена для Vercel.
- Фирменная оболочка Аксон: логотип, тонкая градиентная линия, Inter, карточки и тёмная тема в стиле ДокСлота.
- Адаптивная навигация и отдельные экраны: «Обзор», «Календарь», «Заявки», «Пользователи», «Справочник».
- Календарь трёх общих слотов на дату; заказчику показывается занятость чужих слотов без раскрытия данных чужих заявок.
- Реестр заявок с поиском, фильтром статуса, управлением статусом для рабочих ролей и CSV-выгрузкой.
- Административный экран пользователей: создание, редактирование логина, роли, БЕ и БЕ по умолчанию, смена пароля, включение/отключение доступа.
- Административный экран справочника БЕ/РЦ: добавление, редактирование и деактивация записей.
- Администратор может создавать и редактировать заявки от имени любого активного пользователя с ролью «Заказчик».
- Раздел «Настройки»: месячный лимит заявок по каждой роли и минимальный срок предварительной записи.
- Раздел «История»: серверный журнал создания и изменения заявок, состава груза, пользователей, справочника и настроек; серверный поиск по пользователю, действию и деталям по всему архиву, фильтры по объекту и периоду, постраничная загрузка по 500 событий.
- Неоднозначная промо-плашка «Управляйте транспортным потоком» убрана из обзора для всех ролей.
- Вход по логину и паролю; пароль можно показать/скрыть.
- Добавлен `src/vite-env.d.ts`, чтобы TypeScript распознавал `import.meta.env`.
- Добавлены миграции `0002_admin_workspace.sql` и `0003_admin_controls_audit.sql`: административные права в рамках RLS, серверные лимиты, настройки и журнал аудита.

## Роли

| Роль | Возможности |
|---|---|
| `customer` | Просмотр занятости трёх слотов, создание своих заявок, просмотр своих заявок; изменение своей заявки только пока она имеет статус `created` |
| `dispatcher` | Просмотр всех заявок, изменение данных заявок и статусов |
| `utz` | Просмотр всех заявок, изменение данных заявок и статусов |
| `admin` | Все операционные функции; создание и редактирование заявок от имени заказчика; редактирование пользователей и БЕ/РЦ; настройки лимитов; история действий |

## Важная последовательность обновления Supabase

Применять только в отдельном Supabase-проекте портала заказа транспорта. **Не выполнять в проекте «Аксон ДокСлот».**

1. Если схема `0001_initial_schema.sql` уже была применена при первичной установке портала, повторно её не запускайте.
2. Откройте Supabase → SQL Editor → New query.
3. Полностью скопируйте и выполните файл `supabase/migrations/0002_admin_workspace.sql`.
4. Затем полностью скопируйте и выполните `supabase/migrations/0003_admin_controls_audit.sql`.
5. Разверните обе Edge Functions из этого архива: `admin-create-user` и `admin-update-user`.
6. После успешного выполнения обновите сайт на Vercel.

Миграция `0002`:
- разрешает `INSERT/UPDATE` справочника только в рамках уже существующей admin RLS policy;
- разрешает `UPDATE` профилей только в рамках существующей admin RLS policy;
- усиливает ограничения изменения заявки и её груза для заказчика;
- добавляет `get_slot_occupancy(date,date)`, возвращающую только дату и номер занятого слота;
- пишет в `audit_log` факт изменения роли, статуса и привязки пользователя.

Миграция `0003`:
- добавляет `portal_settings` и `role_request_limits` с начальными значениями: 0 дней предварительной записи и 30 заявок в месяц для каждой роли;
- ограничивает создание заявки активными пользователями роли `customer`, выбранными администратором, у которых назначена действующая БЕ;
- проверяет в базе данных срок предварительной записи и месячный лимит по роли заказчика; отменённые заявки не учитываются;
- добавляет аудит изменений заявок и их состава груза, пользователей, справочника БЕ/РЦ и настроек;
- не позволяет менять тип БЕ/РЦ у записи, которая уже используется в профилях или заявках (код, название и адрес редактируются свободно);
- оставляет чтение `audit_log` только администраторам; запись выполняется триггерами и серверными Edge Functions;
- добавляет защищённые RPC `admin_save_portal_settings` для атомарного сохранения настроек и `admin_search_audit` для поиска по всему журналу с постраничной загрузкой;

Для срока предварительной записи сервер использует бизнес-дату `Europe/Moscow`. Изменение этого правила при переносе процесса в другой регион выполняется в триггере `enforce_transport_request_limits`.

## Создание пользователей из интерфейса

Раздел «Пользователи» создаёт аккаунты через Supabase Edge Function `admin-create-user`. Service Role key остаётся только на серверной стороне функции и не должен попадать в переменные Vercel или клиентский код.

Файл функции: `supabase/functions/admin-create-user/index.ts`.

Перед использованием раздела «Пользователи» обе функции должны быть развернуты в том же Supabase-проекте:

- Supabase Dashboard → Edge Functions → создать/развернуть `admin-create-user` и `admin-update-user`;
- вставить содержимое соответствующих файлов из `supabase/functions/`;
- проверить, что обе функции используют серверные секреты `SUPABASE_URL`, `SUPABASE_ANON_KEY`, `SUPABASE_SERVICE_ROLE_KEY`.

Если функции не развёрнуты, основные экраны заявок и календаря продолжат работать, но создание и редактирование пользователей из интерфейса будет недоступно.

Первый администратор создаётся один раз через Supabase Authentication → Users, затем его UUID добавляется в `public.profiles` с `username`, `role='admin'`, `is_active=true`. Далее пользователей создавайте из административного интерфейса.

## Vercel

- Framework Preset: `Vite`
- Root Directory: `./`
- Build Command: `npm run build`
- Output Directory: `dist`
- Install Command: `npm install`
- Environment Variables для `Production` (и при необходимости `Preview`):
  - `VITE_SUPABASE_URL` — URL отдельного Supabase-проекта портала;
  - `VITE_SUPABASE_ANON_KEY` — Publishable key или legacy anon key этого проекта.

Не добавляйте `service_role` / secret key в Vercel Environment Variables с префиксом `VITE_` или в клиентский код.

После изменения переменных окружения требуется новое развёртывание.

## Локальный запуск

```bash
npm install
npm run dev
```

Проверка production-сборки:

```bash
npm run build
```

## Ограничения текущей итерации

- Сохранение заявки и строк груза пока выполняется несколькими клиентскими запросами; для полной атомарности следующей итерацией следует вынести операцию в транзакционный RPC.
- CSV открывается в Excel, но это не XLSX-книга с форматированием.
- История загружается порциями по 500 событий; кнопка «Загрузить ещё» позволяет просматривать более ранние записи без ограничения архива в базе данных.
- Перед промышленной эксплуатацией обязательны тесты под каждой ролью: создание, изменение, отмена, конкурирующее бронирование одного слота, попытки доступа к чужим заявкам и проверка блокировки пользователя.

## Безопасность и границы проектов

- Клиент использует только `VITE_SUPABASE_URL` и публичный `VITE_SUPABASE_ANON_KEY`.
- Service Role key используется только в Edge Function.
- Все прикладные таблицы используют RLS; миграция `0002` не отключает RLS и не открывает чтение чужих заявок.
- Функция занятости слотов отдаёт только дату и номер слота, не раскрывая детали чужих заявок.
- Не применяйте SQL этой системы к базе данных «Аксон ДокСлот».
